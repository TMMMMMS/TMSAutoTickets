# Design

## Context

V2 已有 Appium 会话、显式等待、配置加载和点击逻辑。现有提交函数忽略点击返回值，总体重试会重建会话并从头执行。已确认真机包名与入口，尚缺目标详情页、场次和确认页的实际控件证据。

## Goals / Non-Goals

设计覆盖单台 Android 真机的一次指定场次购买。用户负责登录、打开演出详情页及付款。Web、旧版脚本和多设备购买在本次范围之外。

## Decisions

- 继续使用现有三个 shell 入口、Poetry、Appium Python Client 和 UiAutomator2。统一 SDK、解释器、驱动和设备发现方式，按设备序列号建会话并保留前台页面。检查命令与购买入口使用同一运行环境。
- 继续读取移动端配置中的城市、日期、票价、观演人和提交开关。关键词可匹配多个演出时要求补全目标；同一日期有多场时使用时间区分。在大麦 9.0.39 的实测中，场次、票档和详情页购买按钮存在空文本。按用户确认的做法，在 macOS 上用系统 Vision 读取这些控件的屏幕区域，按识别结果选择，最后在确认页复核。
- 用当前页面证据区分详情、待开售、可选票、确认及订单结果。沿用显式等待观察销售状态，等待可取消。以真机控件标识、语义和选中状态验证每次页面转移，避免通用“确认”文案触发其他操作。
- 提交在核对完成后独立执行。点击前记录本次会话已进入提交阶段，限制重试入口。驱动发出点击后发生异常时保留待核实状态。可归属到本次提交的订单编号或含目标信息的新订单结果可作为成功依据。
- 演练结束释放驱动会话并保留前台确认页，供用户查看。测试使用现有 pytest 和模拟驱动覆盖提交及异常分支，真机演练采用关闭提交的配置。

## Risks / Trade-offs

- 票档文本不可读或大麦页面更新 → 仅使用能从选择页或订单摘要交叉核对的票档，无法确认时停在提交前。
- 限购、余票不足或平台要求用户操作 → 反馈页面状态，让用户判断下一步。
- 同一票价有不同区域或额外费用 → 按可见票档名称、单价和张数核对，订单总额单独展示。

## Migration Plan

先修复提交开关和结果判断，再接入真机预检及页面核对。更新快速开始说明和示例，用演练先验证新流程。若目标页面不可识别，停止本次运行并保留人工购买入口。
